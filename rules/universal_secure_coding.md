# UNIVERSAL SECURE CODING BASELINE (WEB & APP EDITION)
> Enforceable baseline across all software projects based on the Autonomous AI Security Framework.

## The Five Laws
1. **Evidence is machine-made, not agent-written:** Test results, scan output, SBOM, and provenance are generated by CI, cryptographically signed, and SHA-bound. Agent-pasted logs count as zero evidence.
2. **The judged cannot judge:** Builder never writes gating tests alone, never sees private canary mutations or holdout tests, and holds zero merge rights on protected branches.
3. **LLMs advise, CI decides:** Gates are deterministic required status checks on protected branches enforced through merge queues. The Orchestrator has zero merge rights and zero override authority.
4. **Coverage is reported, not "no issues found":** Every report explicitly lists what was tested, what was not, and what was NOT VERIFIED. Zero tolerance (0% allowed) on Non-Negotiable CRITICAL Controls.
5. **Human review is risk-based, not tier-based:** Any diff touching security-critical logic (authentication, authorization, session management, cryptography, payment/financial logic, file serving, SQL construction, secrets) mandates review and signed approval by a security-competent human across ALL tiers.

## Numbered Controls (Part 8)
- **SEC-AUTHZ-1:** Server-side authorization on every action (BOLA/BFLA test suite, mutation).
- **SEC-AUTHZ-2:** Mandatory tenant/ownership filter in every user-scoped query (IDOR prevention).
- **SEC-AUTHZ-3:** Mass assignment blocked via explicit allow-list DTOs / strong parameters.
- **SEC-AUTHN-1:** Passwords hashed with Argon2id (or bcrypt cost ≥ 12); never reversible.
- **SEC-AUTHN-2:** Rate limiting, account lockout, no user enumeration on login/register/reset.
- **SEC-AUTHN-3:** Single-use, short-lived, hashed-at-rest reset tokens.
- **SEC-SESS-1:** Token revocation on password change, forced logout, account suspension, role change.
- **SEC-SESS-2:** Cookie flags: `Secure`, `HttpOnly`, `SameSite=Lax` or `Strict`.
- **SEC-TOKEN-1:** Zero tokens (`wstoken`, bearer, API keys) in URL query strings or application logs.
- **SEC-INPUT-1:** Allow-list validation, payload size limits, reject unknown fields.
- **SEC-INJ-1:** Parameterized queries only; no string-built SQL/NoSQL/command injection sinks.
- **SEC-OUT-1:** Context-aware output encoding; no raw HTML sinks or innerHTML with user data.
- **SEC-FILE-1:** Upload validation by magic bytes; stored outside web root; forced download on user HTML/SVG.
- **SEC-SSRF-1:** Outbound requests through hardened client with allow-list; metadata/private IPs blocked.
- **SEC-REDIR-1:** Redirect targets validated against an allow-list or strictly local.
- **SEC-HDR-1:** Strict headers: CSP, frame-ancestors, X-Content-Type-Options, Referrer-Policy, HSTS.
- **SEC-CRYPTO-1:** Vetted crypto libraries, CSPRNG, TLS 1.2+ (1.3 preferred).
- **SEC-SECRET-1:** Zero hardcoded secrets in code, config, or logs; vault/KMS integration; full git history scan.
- **SEC-LOG-1:** Security events logged; PII/secrets redacted; tamper-evident log stream.
- **SEC-ERR-1:** Fail closed; no stack traces, database errors, or internal diagnostics exposed.
- **SEC-RES-1:** Strict payload limits, pagination, upload count, and ReDoS regex limits.
- **SEC-RES-2:** Per-user rate limits, per-endpoint quotas, cost caps on expensive operations (AI, exports).
- **SEC-API-1:** Maintain active API inventory; shadow and deprecated routes removed (OWASP API9:2023).
- **SEC-WEBHOOK-1:** Verify webhook signatures, timestamp tolerance, and replay protection.
- **SEC-MAIL-1:** No email header injection; SPF, DKIM, and DMARC enforcement.
- **SEC-IAC-1:** Scanned IaC; least-privilege IAM; no public storage buckets.
- **SEC-SC-1:** Lockfiles with hashes, SBOM per release, signed build artifacts (SLSA L3).
- **SEC-PRIV-1:** Data minimization, retention policies, tested export and deletion flows (DPDP/GDPR).
- **SEC-LLM-1:** Untrusted data separated from system prompts; output treated as untrusted; tool allow-listing.

## Structural Anti-Tampering & Anti-Cheat Controls
1. **Branch Authorization Lock:** Artifacts built exclusively from commits landed via merge queue on protected branch. Workflow files locked via `CODEOWNERS` hash lock.
2. **Test-Touch Detection:** CI fails if a commit modifies both a feature file and its gating test file without Auditor sign-off.
3. **Auditor Holdout Tests:** Private test suite held outside the Builder's repo run in CI against release candidates.
4. **Defective Test Escalation Channel:** When a test is broken or contradictory, Builder submits `/security/test_issue_report.json` instead of modifying the test.
5. **AI Authorship Provenance (NIST SP 800-218A):** CI requires git trailers (`Co-authored-by: Agent`, `X-Authorship: AI`).
6. **Non-Negotiable CRITICAL Controls (0% NOT VERIFIED allowed):** Authn, Authz, Tenant Isolation, Cryptography, Payments/Financial, File Serving, Secrets.

## Mathematical Scoring Formula
- If open CRITICAL findings > 0 $\implies$ **Score = 0% (FAIL)**
- If open HIGH findings > 0 $\implies$ **Score $\le$ 50% (Hard Cap, FAIL)**
- If all CRITICAL and HIGH closed $\implies$ $\text{Score} = \frac{\text{Controls PASS}}{\text{Controls Applicable}} \times 100$
